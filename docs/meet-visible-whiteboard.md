# Whiteboard visibility in Meet

Opening or editing a whiteboard requests automatic presentation, including edits to a board that is already open. Wilco attempts the existing canvas-only screen-sharing adapter first. If Meet cannot start sharing and the bot's camera is enabled, it shows the same board canvas in Wilco's camera tile; participants can pin/enlarge the tile. Subsequent changes update that tile without repeatedly opening the share controls. “Wilco, stop sharing” clears board mode and restores the approved mascot.

Only board data or a verified native FigJam canvas supplies these frames. The camera does not capture the desktop, meeting participants or account UI. A missing/redirected native canvas stops the prior board instead of falling back to unrelated content. Native FigJam still requires the bot's one-time Figma authorization; this change does not create a signed-in session or substitute a local draft for a native file.

Validation: five new backend regression cases cover screen-share success, camera fallback, repeated updates, automatic presentation on edits and unavailable native frames. Synthetic Chromium checks verify real outgoing camera pixels, live frame changes and avatar restoration, plus native-canvas transfer/login suppression. The existing two-peer screen-sharing validation could not complete local ICE negotiation in this environment (both peers remained checking), so remote WebRTC reception and actual Meet visibility are not claimed by these local checks. The outgoing track itself was read as video and checked pixel by pixel.
